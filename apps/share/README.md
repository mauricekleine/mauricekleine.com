# artifact sharing

`artifact-share` serves snapshot copies at `share.mauricekleine.com`. The private
Soliton store remains the source; nothing here reads it. Shares expire 30 days after
their commit, or earlier when deleted.
Workers Builds deploys it from `main` through its own `artifact-share` trigger, which
runs only when `apps/share/`, `packages/superthread/`, `package.json` or `bun.lock`
changes. It builds with `bun install --frozen-lockfile && bun run --cwd apps/share build`
and deploys with `cd apps/share && cf deploy --prebuilt`. Deploys keep the Worker's
existing secrets, so the build needs no credentials beyond its Workers Builds token.
Root `bun run deploy:verify <sha>` waits for both Workers.

## Admin API v1

All `/_admin/*` requests require `Authorization: Bearer <ARTIFACT_SHARE_TOKEN>`.
JSON responses and errors have `Cache-Control: private, no-store`. No CORS.
IDs are 10–32 base62 characters, generated by the CLI (16 characters).

1. `POST /_admin/shares/:id/uploads` with JSON
   `{mode:"public"|"pin", fingerprint:"<64 hex>", salt?:"<32 hex>", pinHash?:"<64 hex>", files:[{path,size}]}`.
   PIN hash is SHA-256 of UTF-8 `salt + ":" + sixDigitPin`. Salt is random per share.
   Returns `201 {upload:"<uuid>"}`. Salt/hash are required only for PIN mode.
2. `PUT /_admin/shares/:id/uploads/:upload/files/:path` with raw file bytes.
   Encode each path component. Length must match the manifest. Returns 204.
3. `POST /_admin/shares/:id/uploads/:upload/commit` switches the pointer only after
   every file is present. Returns `{id,mode,version,fingerprint,updated,expiresAt}`.
   `expiresAt` (ISO 8601) is commit time plus 30 days, set by the Worker; the client
   cannot choose it. Committing to an existing ID (re-sharing) restarts the 30 days.
   Retrying a commit returns the same receipt. Before commit, old content stays live.
4. `DELETE /_admin/shares/:id` immediately revokes access, including cookies; 204
   even if absent. Staging uploads for that ID are also revoked.
5. `GET /_admin/shares` returns `{shares:[{id,mode,version,fingerprint,updated,expiresAt}]}`.
   An expired share can appear until the alarm reclaims it; its `expiresAt` is past.

Limits: 200 files, 100 MiB total, 95 MiB per `.mp4`, `.webm`, `.m4a` or `.mp3` file
(case-insensitive), 10 MiB per other file, 64 KiB manifest. `index.html` is required.
Paths are relative, visible segments, at most 512 characters; dot segments,
backslashes, controls, percent signs, query/hash characters and `_unlock` are rejected.
Upload requests stream into R2 with a bound checked while reading, including chunked
bodies; short or oversized uploads never count as received. The 95 MiB maximum is
99,614,720 bytes, below the [documented request-body ceiling](https://developers.cloudflare.com/workers/platform/limits/#request-and-response-limits)
of 100 MB on Free/Pro (higher on other plans). This repo does not record the account's
plan or a custom upload ceiling. Unknown file
types download as octet-stream; types are determined by extension, never client headers.
Errors: 400 invalid input, 401 missing/bad bearer, 404 missing resource, 409 incomplete
upload, 413 too large. Uploads expire after 24 hours. Replaced/deleted versions and
abandoned uploads are removed by an hourly Durable Object alarm, with retry on failure.

An expired link answers exactly like a deleted one (404), including its PIN form,
unlocks and cookies; PIN cookies never outlive the share. The alarm wakes at the next
share expiry even when nothing else is pending, then revokes the share like `DELETE`
(staged re-shares of the same ID survive) and reclaims its R2 version. Shares stored
before expiry existed have no `expiresAt` and expire 30 days after their `updated`
time (upload start, seconds before commit). When the store starts, or answers
`/_health`, with shares and no pending alarm, as after the first deploy with expiry, it
sets one for the earliest expiry. `deploy:verify` polls `/_health` after each deploy.

## Storage and threat notes

The compatibility date is 2026-10-01, matching the installed workerd/runtime-types
pins (the local runtime cannot yet run a 2026-10-20 date).

One SQLite-backed `ShareStore` Durable Object (`catalog-v1`) owns all share pointers,
upload manifests and per-link attempt windows. This low-volume, single-operator
system favors one serialization boundary over a separate eventually consistent index.
A per-object promise queue serializes reads, uploads, commits, deletes, PIN attempts
and alarms, including R2 and crypto awaits. Stream callbacks can run while an upload
holds the queue; holding `blockConcurrencyWhile` would block the streaming R2 write.
PIN unlock forms (2 KiB cap) are read in full by the front
Worker, before the store's serialized section, so a slow sender cannot stall other links. R2 holds immutable `id/version/path` objects; only the DO
pointer makes them visible. Existing in-flight responses can finish after deletion.
Each request sees one committed version; a page loading assets during replacement
can span versions. Re-share replaces the whole snapshot and invalidates prior cookies.

Artifacts must be self-contained, in both modes, just as on the private vhost.
The required opaque-origin sandbox and no-CORS policy prevent same-host ES modules,
web fonts and `fetch()` of sibling files from loading. Inline scripts/styles/data,
embedded images and external fonts with CORS (such as Superthread's public fonts)
work. In PIN mode, the browser also withholds SameSite=Lax cookies from opaque-origin
subresource requests, so embed images/styles rather than relying on sibling files.
Assets and PDFs remain available as direct top-level links after unlocking; their
HTTP MIME behavior does not imply they can be fetched by a sandboxed document.

Every committed file advertises `Accept-Ranges: bytes`. Single byte ranges
(`bytes=a-b`, `bytes=a-`, `bytes=-n`) return 206 with `Content-Range` and the selected
`Content-Length`; end positions beyond the file are clamped. Unsatisfiable ranges
return 416 with `Content-Range: bytes */<size>` and an empty body. Multi-range and
malformed range headers receive the full 200 response. `HEAD` returns the same
headers as `GET`, without a body. PIN checks happen before range handling: without
a valid cookie, even a media range request receives the PIN form. After unlocking,
direct top-level media links carry the cookie; sandboxed subresources still do not.

Five wrong PINs within one hour lock that link for one hour from the fifth attempt.
A correct PIN does not reset the failure window; re-sharing also preserves lockout.
A locked link rejects unlocks, including correct PINs; existing valid cookies still
work. Lockout is intentionally per link, so visitors can deny unlocks for an hour.
Online guessing is bounded; a six-digit PIN is not strong protection against an
R2/DO reader doing offline enumeration. Only salted hashes reach the Worker.

Bearer digests use Workers' native constant-time comparison. Cookie HMACs use native
Web Crypto verification and bind ID, immutable version, expiry and purpose. Cookies
are Secure, HttpOnly, SameSite=Lax, host-only, scoped to the link, and last 30 days
or until the share expires, whichever is sooner.
Changing the PIN rotates the version. All bodies use `private, no-store`, including
public snapshots, to make revocation and mode changes immediate at the server.

All non-PDF responses carry the private vhost's opaque-origin CSP sandbox. Artifacts
cannot read/set cookies or read PIN pages, even though the URLs share a host. The PIN
form has no script and receives a signed random, version-bound, ten-minute challenge;
POSTs without it never count. Its opaque sandbox produces `Origin: null`, so origin
checking alone would be insufficient. No CORS means sandboxed scripts cannot fetch
a challenge, and `frame-ancestors 'none'` prevents embedding/clickjacking the form.
The form action is bound to its link, tokens cannot move between links, and only GET/
HEAD content and the exact unlock POST route are allowed. PDFs omit sandbox for the
browser viewer, carry nosniff, and are served only as application/pdf. Uploaded HTML
cannot impersonate an admin route, overwrite a PIN page or register a service worker.
Every response has noindex/nofollow, no-referrer and nosniff. Logs never record bodies,
cookies, bearer tokens or PINs.

## Local verification

From the root, `bun run test` includes Miniflare/workerd R2 + SQLite DO HTTP tests.
`bun run --cwd apps/share dev` starts a loopback local Worker with disposable test
credentials; use its URL only for fixtures. It never accesses Cloudflare or 1Password.
The CLI supports `MK_ARTIFACT_SHARE_URL` (HTTPS, or loopback HTTP for local testing)
and `MK_ARTIFACT_SHARE_TOKEN` environment overrides. The default token is read from
`op://Soliton Agents/ARTIFACT_SHARE_TOKEN/credential` without logging it.

`GET /_health` returns `{sha}` from the build's `BUILD_SHA` through the store, with the same security
headers. `bun run --cwd apps/share build` stamps HEAD; `cf deploy --prebuilt --dry-run` from `apps/share` validates
the independent build without touching the existing web Worker.

## One-time M5 setup

Run from a fresh checkout of this repo on the M5, after loading `mk-cloudflare` and
`mk-1password`. Select Kaulos (`cloudflare-account --name` from this repo). Keep the
R2 bucket private with no r2.dev or custom bucket domain. The Worker is its only reader.

Create two **API Credential** items in **Soliton Agents**, with a concealed built-in
`credential` field and notes naming the readers and scope. The admin token authorizes
all share changes; the cookie key signs only sessions/forms. Neither expires.
These commands generate 32 random bytes per item and pipe JSON directly into the
M5 desktop app (Touch ID). They print no credentials and create no secret files:

```bash
set -o pipefail
cloudflare-account --name  # must say kaulos
for item in ARTIFACT_SHARE_TOKEN ARTIFACT_SHARE_COOKIE_KEY; do
  python3 - "$item" <<'PYSETUP' | op item create --account mauricekleine.1password.com --vault "Soliton Agents" --format json - >/dev/null
import json, secrets, sys
title = sys.argv[1]
notes = ("Artifact sharing admin bearer; read by mk artifacts on Soliton and by the artifact-share Worker; authorizes upload, replace, list and delete."
         if title == "ARTIFACT_SHARE_TOKEN" else
         "Artifact-share Worker HMAC key; signs link/version-bound cookies and PIN forms; read only for deployment.")
print(json.dumps({"title": title, "category": "API_CREDENTIAL", "fields": [
    {"id": "credential", "label": "credential", "type": "CONCEALED", "value": secrets.token_hex(32)},
    {"id": "notesPlain", "purpose": "NOTES", "type": "STRING", "value": notes}]}))
PYSETUP
done
op read "op://Soliton Agents/ARTIFACT_SHARE_TOKEN/credential" >/dev/null
op read "op://Soliton Agents/ARTIFACT_SHARE_COOKIE_KEY/credential" >/dev/null
bun install --frozen-lockfile
bun run --cwd apps/share build
cf r2 buckets create --name artifact-share
op inject -i apps/share/secrets.json.tpl |
  (cd apps/share && cf deploy --prebuilt --secrets-file /dev/stdin)
curl --fail --silent https://share.mauricekleine.com/_health
```

First deploy provisions the SQLite Durable Object migration for exported `ShareStore`,
binds private R2 `artifact-share`, installs both secrets in that same deployment and
attaches **only** `share.mauricekleine.com`. `exports.durableObject({storage:"sqlite"})`
is cf's migration declaration; no separate Wrangler migration is needed. Existing
`mauricekleine-com` and all four of its domains are untouched. Later releases deploy
through Workers Builds. Rotate a secret by repeating the `op inject | cf deploy`
pipeline. Root `bun run deploy` deploys only the web app.

After the dotfiles refresh, run `mk artifacts share <project>/<slug> --public` or
`--pin` from the M5/Soliton and open the result. No Soliton Cloudflare credential or
S3 key is needed. 1Password's existing read-only Soliton service account already sees
Soliton Agents; confirm `op read ... >/dev/null` there, without changing vault access.
